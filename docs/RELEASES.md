# 版本与镜像发布

本页面向发版维护者，统一维护 Release、镜像和工作流约定。新人获取依赖只需 [快速开始](QUICKSTART.md#获取依赖包)，算法 PR 的批准和成绩回传见 [贡献指南](../CONTRIBUTING.md#审查与服务器实验)。

## 当前版本与来源

当前统一环境版本是 [26-11-1](https://github.com/Kunlun-APERTURE/APERTURE_vision_26/releases/tag/26-11-1)，保留预发布标记。主仓库 main 已合入该环境。源码可选择当前 main 开发，也可检出具体 Release 复现；每次切换版本后，重新按该检出的依赖清单准备环境和构建算法。

GitHub 的 Latest 不指向预发布版本，因此旧正式版可能仍显示此徽标。当前推荐环境以本页固定链接及源码清单为准，不使用 releases/latest 作为新人入口。

单一包为 `ghcr.io/kunlun-aperture/aperture_vision`，项目显示名为 APERTURE_vision。一个镜像包含所有开发与实验依赖，模拟器、桥接、算法和评分分别使用独立容器。镜像清单是 [release/dependencies.json](../release/dependencies.json)，镜像获取位置和离线备用文件只在快速开始维护。

|内容|唯一记录位置|用途|
|---|---|---|
|当前源码所需环境|`release/dependencies.json`|固定一个镜像 digest、本地名称、构建来源与验收记录|
|某次发版的完整对应关系|该 Release 的 `aperture-dependencies.json` 附件|固定该版本镜像和主仓库／子仓库提交|
|镜像构建时的源码|清单 `build_sources`|镜像未重建时保持原来源|
|本次发版的源码|Release 附件 `release_sources`|主仓库取 Git 标签对应提交，子仓库取该提交的 gitlink|
|GPU 与组件验收|清单 `acceptance` 指向的报告|SHA256 与镜像身份必须匹配|

Git/Release 标签和镜像日期统一写作 `年-月-日`，例如 `26-11-1`。旧标签 `26-11-01` 保留用于历史追溯，不能为新版本再次使用：它与 `26-11-1` 会映射到同一个镜像标签。已有发布标签不得移动或覆盖；同一天的修订先留在 main，待下一日期发版。

## 工作流职责

|工作流|触发|执行内容|
|---|---|---|
|开发检查|PR 或 push 到 main|Python 测试与覆盖率，不运行 GPU 实验或发布镜像|
|实验申请|非作者审查者批准当前 PR|保存请求；工作站另行校验 CI、批准和实验选择|
|实验结果|工作站派发|将成绩和文本日志保存为附件|
|发布统一镜像|Release 发布，或手动输入已存在的标签|复用已验收镜像，验证匿名下载并附加版本清单|

四个入口和原有 job/artifact 标识保持独立；修改工作流显示名称不应改动服务依赖的机器标识。

## 发版前准备

1. 合并改动到 main，确认“开发检查”通过；记录要发布的完整提交 SHA。镜像验收与源码测试分别判断，Python CI 不包含 GPU 实验。
2. 仅修改算法源码或文档、且平台和依赖不变时，保持镜像清单不变。发版只为原镜像添加新日期标签，镜像 digest 可以与前一版本相同。
3. 更新系统依赖、工具链、模拟器或镜像入口时，先完成新候选的构建、组件测试和全服务同镜像闭环，再更新清单中的固定身份、build_sources 和 acceptance。Rust 既有失败及新增失败必须明确记录。
4. 确认候选镜像已上传同一个 GHCR 包且可按固定 digest 读取。常规发版只复制已验收镜像，不从 Dockerfile 重建，也不从工作站导出镜像。

已有统一镜像的维护构建见 [运维指南](OPERATIONS.md#维护构建)，日常算法和模拟器源码编译见 [开发指南](DEVELOPMENT.md)。全服务验收范围和已知 Rust 失败见 [能力与限制](STATUS.md)。

## 发布与自动执行

在 GitHub 的 Releases 页面选择 main 中已检查的提交，填写日期标签和中文说明，说明具体变化、验证和已知限制，然后发布。需要先审查说明时保存为草稿；草稿发布后才触发流程。正式版和预发布都运行同一个 [发布统一镜像](../.github/workflows/dependency-release.yml) 工作流。

自动步骤依次为：检出日期标签 → 检查单一镜像清单及验收报告 → 按固定 digest 复制为本次日期标签 → 匿名下载全部层 → 给同一 Release 附加 `aperture-dependencies.json`。

工作流用临时 GITHUB_TOKEN 写入 GHCR 和 Release 附件，不运行 GPU 实验。所有发布任务串行，避免不同写法的历史日期并发操作同一镜像标签。此流程不会触发 PR 服务器算法实验，PR 实验也不会发布镜像。

只有运行成功、清单附件出现且其中 release_sources 对应本次 Git 标签时，才算镜像发布完成。Artifacts 中的清单仅供诊断，不能替代成功附加到 Release 的清单。Release 自动生成的源码压缩包不含子模块，给新人应提供递归克隆说明及快速开始链接。

发布说明只描述本次变化、实际验证和限制，获取和运行步骤引用该标签下的快速开始，不复制整套安装或实验流程。预发布标记、是否为 Latest 应按实际成熟度明确设置；历史版说明顶部标记历史用途并指向当前版本，不重写历史成绩。

## 失败与恢复

从 Actions 查看“发布统一镜像”的失败步骤。网络或 GHCR 访问设置修复后，在同一工作流选择 main，输入已经存在的 Release 日期重新运行；工具和清单仍从该日期标签检出。

- 已有同内容镜像标签可复用；已有不同内容标签直接失败，不覆盖。
- 已有同内容 Release 清单可重复核对；已有不同内容清单直接失败，先查明版本差异。
- 上传镜像成功但匿名下载失败时，不能对新人宣称可用。当前 aperture_vision 已公开；仅创建新包时需要一次性设置 Public。
- 旧五镜像版本不走当前重试入口，使用其历史说明。首次迁移工作流和来源清单已保存在 [迁移归档](../archive/20261101-image-migration/README.md)，退出日常 Actions。

维护者已安装 Skopeo 时，可从仓库根目录进行公开读取检查：

```bash
python3 tools/dependency_registry.py verify-public --download
```
